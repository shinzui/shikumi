# ECTA (equality-constrained tree automata) — evaluation and what to borrow

This is an **idea / evaluation note**, not an ExecPlan. It records the conclusion of an
evaluation of the ECTA library and the ICFP 2022 paper *"Searching Entangled Program
Spaces"* (Koppel, Guo, de Vries, Solar-Lezama, Polikarpova) against shikumi, so that the
reasoning is not lost and a future reader does not re-investigate from scratch.

- Paper: *Searching Entangled Program Spaces*, Proc. ACM Program. Lang. 6, ICFP, Art. 91
  (Aug 2022). https://doi.org/10.1145/3547622
- Library evaluated: `ecta` Haskell package (v1.0.0.4, BSD3), local checkout at
  `/Users/shinzui/Keikaku/hub/haskell/ecta-project`. Upstream: https://github.com/jkoppel/ecta

## Bottom line

**Do not integrate the ECTA library into shikumi.** It is excellent work, but its sweet
spot sits at a layer shikumi does not have, and shikumi's actual bottleneck is exactly the
thing ECTA cannot help with. There is **one** research-grade opportunity (type-driven
synthesis of shikumi pipelines) that is interesting but uneconomical today, and **one idea
worth borrowing** (dependent joins → cross-field output constraints) that is a ~50-line
plain-Haskell feature, not a library dependency.

## What ECTA actually is

A data structure for **compactly representing astronomically large spaces of first-order
terms with *dependent joins*** — equality constraints between subterms (e.g. "the
argument's type must equal the function's parameter type"). Two superpowers:

1. **Compact representation** of *entangled* spaces via hash-consed shared subterms, where
   VSAs / e-graphs / finite tree automata cannot, because their joins are *independent*.
2. **Efficient enumeration** of terms satisfying those equality constraints, via *static*
   reduction (prune the automaton before enumerating) and *dynamic* reduction (postpone
   constrained choices via unification variables during enumeration).

Killer app: **Hectare**, a type-driven program synthesizer — enumerate well-typed Haskell
terms from a component library, ~7× faster than Hoogle+ in ~1/10 the code. Also encodes
SAT (as a generality proof). The recurring shape: **a discrete term space over a known
signature, where validity is a *symbolic, decidable* predicate (type-checking, clause
satisfaction), and the goal is to *enumerate* members.**

## Why it does not fit shikumi's optimization layer

Shikumi's `shikumi-optimize` (COPRO/MIPRO/GEPA/KNN/Bootstrap) searches a space of
**(instruction, demo-set)** pairs. Match that against what ECTA requires:

| ECTA needs | shikumi's optimization has |
|---|---|
| Discrete terms over a finite signature | Instructions are **natural-language strings generated by an LLM proposer** — no grammar to enumerate; the generator is itself a model |
| Validity = symbolic, decidable predicate | Quality = **black-box metric requiring real LM calls over a dataset** — noisy, expensive, undecidable |
| Bottleneck = representing / enumerating the space | Bottleneck = **the eval oracle** (LM call cost), not combinatorics |
| Goal: enumerate satisfying members | Goal: find the **highest-scoring** candidate under a costly noisy metric |

The last row is the crux. Shikumi's problem is **sample-efficient black-box optimization**
(Bayesian-opt / bandit territory — which MIPRO's TPE-surrogate and GEPA's Pareto evolution
already approximate). ECTA is a **constraint-satisfaction enumerator**. The demo-selection
subspace (choose *k* of *n* examples) *is* discrete and combinatorial, but it is tiny, has
no equality constraints entangling the choices, and KNN/brute-force already handles it. The
one thing ECTA uniquely provides — dependent joins — has nothing to entangle here.

## The places it superficially looks like a fit — and why each fails

- **Structured decoding / constrained output.** Most plausible-sounding match. But shikumi
  enforces structure via the **provider's native `response_format`** or a fallback adapter +
  post-decode validation. It is a remote-API client (via baikai) with **no logit access**,
  so it cannot do token-level grammar-constrained decoding — which is the only place a tree
  automaton would earn its keep. And shikumi's constraints (`MinLen`/`MaxLen`/`EnumOneOf`,
  per-field bounds) are exactly *not* the cross-subterm equality constraints ECTA exists
  for. Overkill and architecturally misplaced.
- **ReAct action grammar / tool-call validation.** Real, but a flat grammar with no
  entanglement — does not justify a ~3000-LOC automaton library.
- **Type-driven program generation.** Shikumi's `Program i o` pipelines are *authored* by
  the user in Haskell, not enumerated. There is no synthesis to accelerate.

## The one genuinely ECTA-shaped opportunity (parked)

**Type-driven synthesis of shikumi pipelines.** Use ECTA exactly as Hectare does:
enumerate well-typed compositions of modules (`Predict`, `Compose`, `Map`, `Parallel`, …)
that match a given input/output `Signature`, with equality constraints enforcing that
composed nodes' types line up. This is a correct, honest use of dependent joins.

Why it is parked rather than planned:

- The space of *useful* LLM pipelines is small and usually hand-designed.
- Every enumerated candidate still costs a full dataset eval to score — so enumeration was
  never the bottleneck; you would build a synthesizer whose output you cannot afford to
  evaluate.
- GEPA/MIPRO already do structure-adjacent search at the prompt level.

Revisit only if (a) eval becomes cheap (strong offline surrogate metric), and (b) the
module space grows large enough that hand-design stops scaling.

## Engineering blockers (even if the fit were there)

- **Concurrency mismatch.** ECTA uses `unsafePerformIO` global hash-cons caches that are
  **thread-unsafe**. Shikumi is built on `effectful` with a `Concurrent` effect and
  `runProgramConc`. A single-threaded mutable-global library under a concurrent runtime is
  a real impedance mismatch.
- **Dated stack.** ECTA targets GHC 9.0.2 / LTS-18.25; depends on `intern`, `hashtables`,
  `equivalence`, `language-dot`, `pipes`. Research artifact (activity tailing off ~2024),
  not a dependency-grade maintained library.
- **NP-hard enumeration.** Extraction is at least as hard as SAT (proven by reduction).
  Fine for offline type synthesis; not a property you want on a hot path.

## What is worth stealing (the idea, not the code)

**Dependent joins as cross-field output constraints.** Shikumi's `Constrained '[...]`
vocabulary (EP-26, `Shikumi.Schema.Types`) is strictly *per-field*. ECTA's core idea —
constraints that *relate* two subterms (`path A = path B`) — maps cleanly onto a feature
shikumi lacks: **cross-field constraints**, e.g.

- output field `total` must equal the sum of `items`,
- `answer` must be one of the input `choices`,
- two output fields must be mutually consistent.

This is a natural next entry in the `Constraint` kind plus a validator pass — implementable
in plain Haskell (~50 lines), no automaton needed. The paper is a good articulation of
*why* entangled/dependent constraints matter as a class; that framing could sharpen a
future extension of EP-26's constraint model. If pursued, write it as its own ExecPlan.

## Pointers (for whoever revisits this)

- Shikumi optimizer search plumbing: `shikumi-optimize/src/Shikumi/Optimize/Search.hs`
  (`selectBest`, `scoreOn`); strategies under `shikumi-optimize/src/Shikumi/Optimize/`.
- Program GADT + parameter traversal: `shikumi/src/Shikumi/Program.hs`
  (`paramsTraversal`, `nodeFieldsIndexed`).

  `shikumi/src/Shikumi/Schema/Types.hs` (`data Constraint`, `Constrained`).
- ECTA core types/ops if ever needed: `Data.ECTA` (public API),
  `Data.ECTA.Internal.ECTA.{Type,Operations,Enumeration}`, `Data.ECTA.Paths`
  (`mkEqConstraints`); Hectare encoding in `Application.TermSearch.TermSearch`.
